# 규칙 계층(Tier 1) 통합 — 인계 문서

작성 2026-08-11 · 갱신 2026-08-11(병합 후) ·
PR https://github.com/gwanhuiGIM/0730_cobo2_personal/pull/1

이 문서를 읽는 사람이 알아야 할 것은 넷이다. **무엇이 붙었는지**, **어디까지
확인됐고 무엇이 아직 안 됐는지**, **잘못되면 어떻게 되돌리는지**, 그리고
**어떤 종류의 고장이 조용히 일어나는지**(§6 — 여기가 가장 값비싼 절이다).

> **이 브랜치는 `vla_integ`를 이미 받아 병합한 상태다.** 저쪽이 2026-08-11에
> `robot_node`·`wrist_grasp_node`와 부속 약 6,300줄을 지우고 cobot2_ws의
> `pick_fsm`에 실행을 일임했는데, 그 정리를 여기서 먼저 받고 충돌을 이쪽에서
> 풀었다. 받는 쪽이 남의 코드를 보며 충돌을 푸는 상황을 만들지 않기 위해서다 —
> 그때 나온 두 문제(§6-D, §6-B)는 이 코드를 쓴 사람이 아니면 알아채기 어렵다.

---

## 0. 먼저 알 것 — 끄는 것이 파라미터 한 줄이다

```yaml
# src/vla_system/config/system.yaml
vla_agent:
  ros__parameters:
    skill_tier_enabled: true           # ← 기본값 (2026-08-11부터)
    rule_store_path: "~/.ros/vla_rules.json"
```

**이 값이 false면 `agent_node`는 통합 이전과 완전히 같이 동작한다** — 모든
발화가 LLM으로 가고, 세션을 넘는 기억이 없다. 되돌리기가 revert가 아니라
파라미터 한 줄인 것은 의도한 설계다. 실기에서 문제가 생겼을 때 코드를 되감는
것보다 값을 바꾸는 편이 빠르고 안전하다.

**기본값이 처음에는 false였다(2026-08-11 오전 → 오후에 뒤집음).** 계층이
검증되는 동안 머지해도 아무것도 안 바뀌게 하려던 것이었는데, 그 사이에 이
플래그가 조용히 무시되는 배선 결함이 두 번 나왔다(§6-B). 둘 다 "켰다고
생각했는데 안 켜져 있었다"는 같은 모양이었고, 기본이 꺼짐인 한 그 실패는
계속 조용할 수밖에 없다. 측정이 끝난 지금(§7) 기본을 켜짐으로 두는 편이
맞다 — **끄는 쪽이 더 안전한 설정도 아니다.** 이 계층은 자기 동작을 새로
만들지 않고 거르기만 하며, 가위를 확인 없이 집지 않게 막는 것도 이쪽이다.

## 1. 무엇이 붙었나

`agent_node` **앞에** 규칙 계층을 세웠다. 교체가 아니라 추가다.

```
발화 → agent_node.route()
        │
        ├─ 규칙으로 되는가? ──예──→ publish_action()    (LLM 호출 없음)
        │
        └─ 안 되면 ─────────────→ decide()   = 기존 대화 경로 그대로
```

**둘 다 같은 `publish_action`으로 나간다.** 그래서 `vla_pick_bridge_node`도
cobot2_ws도 이 계층이 생긴 것을 알 수 없다. 저쪽 코드는 한 줄도 안 고쳤다.

### 1-B. "이거 집어줘" — 라벨 그려진 화면도 같이 간다

`scene`(JSON)만으로는 **이 발화를 풀 수 없다.** 클래스도 색도 위치도 없고, 뜻은
전적으로 사람이 무엇을 가리키느냐에 있다 — 좌표를 더 촘촘히 실어도 해결되지 않는
종류의 부족함이라 그림을 보여주는 수밖에 없다.

`perception_node`가 이미 내보내던 `/vla/perception/annotated_image`를 쓴다. 거기
그려진 박스 라벨은 `object_id(class, track_id)` — **모델이 JSON에서 읽는 id와 같은
문자열**이다(`detector.draw_tracks`). 모델은 가리켜진 박스를 본 뒤 그 라벨을 그대로
도구 인자에 쓴다. **그림과 JSON을 잇는 끈이 이 라벨 하나뿐이라, 라벨 형식을 바꾸면
이 기능이 조용히 망가진다.**

값이 터지지 않게 세 가지를 정했다.

| 결정 | 이유 |
|---|---|
| **대화 기록에 안 넣는다** | 기록은 60개까지 쌓인다. 이미지가 섞이면 매 호출마다 지난 사진이 전부 다시 올라가 비용이 턴 수에 제곱으로 는다. `attach_image()`가 기록이 아니라 **호출 직전의 사본**에만 얹는다 |
| **사용자가 말했을 때만** | "동작이 끝났다"는 애매할 수가 없어 사진이 풀 것이 없다. 안 그러면 여러 개 담는 미션의 매 단계마다 값을 낸다 |
| **도구 루프 첫 라운드만** | 2라운드부터는 도구 결과를 소화하는 중이지 테이블을 다시 읽는 것이 아니다 |

640×480 프레임이 **422 토큰**이다. 오래된 프레임은 안 보낸다
(`vision_max_age_s`, 기본 2초) — 카메라가 멎었는데 옛 사진을 보내면 모델은 이미
치워진 물체를 자신 있게 가리킨다. 사진이 없는 것보다 나쁘다, 답이 나온 것처럼
보이니까. `vision_enabled:=false`면 구독조차 안 만든다.

**Tier 1은 이 발화를 일부러 안 받는다.** `classes`를 비운 채 `pick`으로 내려가면
대상 한정이 없는 지시가 되어 테이블 위 전부를 집는다. 파서 프롬프트가 가리키는
말을 `other`로 두어 위층으로 넘긴다 — 단 `"여기 있는 거 다 담아줘"`처럼 "다/전부"가
붙어 범위를 가리키는 것은 손가락이 필요 없으므로 `pick`이다(§6-C).

### `skill_tier.py`가 ROS를 모르는 이유

필요한 것을 `SkillHost` 프로토콜로 요구한다.

```python
class SkillHost(Protocol):
    def say(text) / ask(text) / pick(object_id, reason)
    def escalate(reason, text, mission_text)
    def scene_items() -> list[SceneItem]
    def note(event) / record(tier, detail) / turn_done()
```

`agent_node`가 ROS 토픽으로 구현하고, 평가 하네스가 가짜 로봇으로 구현한다.
**둘이 같은 판단 코드를 돌리므로 측정한 것이 곧 나가는 것이다.** 사본을 두면
반드시 갈라지고, 갈라지는 순간 실험 결과가 운영 코드를 보증하지 못한다.

먼저 **끄면 아무것도 안 바뀌는지**부터 본다. 기본이 켜짐이니 이건 명시적으로
꺼서 확인해야 한다.

source install/setup.bash

평소 쓰던 방식으로 한 바퀴 돌려 **말투와 동작이 예전과 같은지** 본다. 다르면
통합이 뭔가 건드린 것이므로 켜고 쓰기 전에 원인을 찾아야 한다.

### 2-2. 규칙 계층만 단독으로 (로봇 없이)

```bash
# 가짜 무대 -- 카메라도 팔도 없이 돌린다.
# --no-position 이 cobot2_ws 연동 구성(테이블 보정 없음)을 흉내낸다. 그냥 두면
# 이 ws가 좌표를 잡은 상태가 되어 §6-D의 버그가 재현조차 안 된다.
python3 -m eval.dryrun_stage --no-position --point-at cup_4 &
ros2 launch vla_system vla_system.launch.py \
  enable_perception:=false enable_realsense:=false enable_pick_bridge:=false \
  rule_store_path:=/tmp/rules.json      # 진짜 파일을 더럽히지 않는다
```

무대는 라벨 그려진 화면도 내보내고, 그 위에 **화살표**를 그린다 — 사람 손가락
대역이다. 돌리는 중에 옮길 수 있다:

```bash
ros2 topic pub --once /dryrun/point_at std_msgs/String "{data: 'scissors_5'}"
```

GUI(`ros2 run vla_system vla_gui`)로 해도 된다 — 체크박스에서 **"카메라 인식"과
"cobot2_ws FSM 연동"을 끄고** "규칙 계층 (Tier 1)"을 켠 채 시작하면 위와 같은
조합이 된다. 확인할 것:

| 발화 | 기대 |
|---|---|
| "사과 다 담아줘" | `/vla/robot/action`에 사과 개수만큼 나온다. **LLM 로그가 안 찍힌다** |
| "바나나랑 컵 빼고 다 담아줘" | 바나나·컵을 **안** 담는다 (정반대로 하면 즉시 중단) |
| "여기 있는 거 다 담아줘" | 담는다. **`-> llm`이 안 찍혀야 한다** (찍히면 §6-C 회귀) |
| "가위 가져와" | `ask_clarification`이 먼저 나온다 |
| "이거 집어줘" (화살표 있음) | 가리킨 것을 집는다. 화살표를 옮기면 답이 바뀐다 |

### 2-3. 🔴 브리지와 함께 (여전히 미검증)

**여기가 가장 위험하다.** `vla_pick_bridge_node`와 함께 띄운 적이 아직 없다.

```bash
ros2 launch vla_system vla_system.launch.py \
  motion_enabled:=false enable_pick_bridge:=true
```

`motion_enabled:=false`로 시작한다. 확인할 것:

- 규칙 계층이 낸 `RobotAction`이 브리지를 통과하는가
- `place`가 빈 문자열로 가고 cobot2_ws가 기본값(basket)으로 받는가
- `request_id` 대조가 깨지지 않는가 (계약 §2)
- `class` 허용 목록에 우리가 쓰는 이름이 다 있는가 (계약 §6 — **일부 거부될 수 있다고
  적혀 있다**)

### 2-4. 실기

`dry_run:=true` + `require_approval:=true`부터. cobot2_ws 쪽 기본값이 그렇게
되어 있으니 그대로 둔다.

## 3. 되돌리기

| 상황 | 방법 |
|---|---|
| 규칙 계층이 이상하게 군다 | `skill_tier_enabled:=false`. 즉시 예전 동작 |
| 규칙이 잘못 쌓였다 | `rm ~/.ros/vla_rules.json` 또는 대화로 "그거 잊어버려" |
| 규칙을 아예 안 남기고 싶다 | `rule_store_path:=""` — 메모리에만 |
| 사진(비전)만 끄고 싶다 | `vision_enabled:=false`. 구독조차 안 만든다 |
| 코드를 되감아야 한다 | PR #1 전체를 revert. 병합 커밋(`01e4277`)이 vla_integ의 삭제 정리를 함께 받았으므로 **개별 커밋만 골라 되감으면 안 된다** |

**장기 규칙 파일이 어디에 쌓이는지 알아두는 게 좋다.** `~/.ros/vla_rules.json`이
기본값이고, 여기에 사용자가 말한 금지·상시 지시가 누적된다. 실기 시험 중에는
매번 지우는 편이 헷갈리지 않는다.

## 4. `place`를 어떻게 다루기로 했나

**규칙 계층에는 목적지 칸이 없다.**

```python
def pick(self, object_id, reason):
    self.publish_action("pick_and_place", object_id, reason, "")   # place 비움
```

빈 문자열이므로 브리지/cobot2_ws 기본값(`basket`)이 적용된다 — 계약 §2/§5.

목적지를 말한 발화("저기다 놔")는 규칙이 표현할 수 없으므로 **대화 경로로 넘어간다.**
거기에는 `place` 칸이 있다. 규칙은 확실한 것만 처리하고 나머지는 위임하는 것이
이 구조의 원래 설계다.

스키마에 `place`를 넣는 선택지도 있었으나 하지 않았다. 필드가 늘수록 파서가
억지로 채우는 경향이 있고, 실제로 `correct` 필드가 그 문제로 불안정하다(§6).

## 5. 규칙 계층이 무엇을 하고 무엇을 안 하나

### 한다

- 클래스·색으로 후보 좁히기, 개수 세기
- 제외 (`"바나나랑 컵 빼고"`)
- 금지 규칙 등록·적용, 이유가 있으면 장기 보존
- 상시 지시 (`"사과 보이면 계속 가져와"` → 범위 되묻기)
- 같은 부탁 3회 반복 시 상시 전환 제안
- 위험물(가위·칼) 확인 — **세션 한정.** 새 프로세스는 다시 묻는다
- 기억 조회 (`"뭐 기억해?"`), 삭제 (`"그거 잊어버려"`)

### 안 한다 (일부러)

의도 해석 전부. `"아까 그거"`, `"그건 말고"`, 조건문, 순서 지정은 **적을 칸을
만들지 않았다.** 칸을 만들면 파서가 억지로 채우고, 채워진 규칙은 "성공했지만
틀린" 상태가 된다. 이건 실험에서 실제로 겪은 실패 방식이다 — 초기 하이브리드가
중간 정정에서 무너진 원인이 정확히 그것이었다.

`"이거 집어줘"`도 여기 속한다. 뜻이 문장이 아니라 **손가락**에 있어서 어떤 칸을
만들어도 담기지 않는다 — 사진을 보는 위층이 받는다(§1-B).

**그래서 못 하는 것은 조용히 틀리는 대신 위임한다.**

## 6. 알려진 한계 (실기 전에 알고 있어야 함)

| 한계 | 심각도 | 대응 |
|---|---|---|
| **정정(`correct`) 파싱이 불안정하다.** 한 문장에서 `intent`·`replaces`·`classes`를 동시에 맞춰야 해서 회차마다 흔들린다 | 중 | 실패해도 **안전 방향**(옛 규칙이 남아 과하게 조심). 사용자에게 `"뭐 기억해?"`로 확인하도록 안내 |
| **"오늘은 A니까 B하지 마"에서 되묻지 않고 짐작한다.** 짐작이 맞긴 했다 | 하 | 안전 방향. 그대로 둠 |
| 조사 처리가 거칠다 — `"컵은(는)"` | 하 | 말투 문제. 기능 무관 |
| 위험물 게이트가 쉬운 명령에서도 뜬다 | 하 | 안전 방향. 시나리오 기대와 다를 뿐 |
| **`track_id`가 재검출 시 바뀐다.** 후보 정렬에 쓰는데 실험에서는 고정이었다 | **미상** | 실기에서 봐야 함 |
| **동작 실패(`last_result="failed"`) 후 재시도 정책이 없다** | **미상** | 실기에서 봐야 함 |

마지막 둘이 진짜 위험이다. **실험 하네스가 재현하지 않은 것들**이라 아무 데이터도
없다.

원래 여기 셋째로 "카메라가 30Hz로 갱신되는 중 미션이 진행되면?"이 있었다.
`eval/dryrun_stage.py`로 진짜 ROS 그래프 위에 올려 보니 바로 터졌다 — **같은
사과를 두 번 집었다.** 팔과 카메라가 다른 시계로 도는 탓에 방금 집은 물체가
최신 스냅샷에 아직 남아 있는데, 후보를 장면에서만 고르고 있었다. 하네스는 이걸
보여줄 수 없었다(드라이버가 결과를 보고하기 *전에* 장면을 갱신한다). 이미 보낸
물체를 미션이 기억하도록 고쳤고(`baa54a5`), 회귀 테스트가 있다.

### 6-B. 조용히 안 켜지는 배선 — 두 번 났다

같은 날 두 번, 규칙 계층이 **켠 줄 알았는데 안 켜진 채** 돌았다. 둘 다 예외를
던지지 않아서, 증상은 며칠 뒤 "말한 규칙이 재시작하면 사라진다"로만 보였다.

1. launch가 `skill_tier_enabled`를 **선언만 하고** `agent_node`의
   `parameters=[]`로 넘기지 않았다. `ros2 launch ... skill_tier_enabled:=true`가
   조용히 무시됐다. `ros2 run --ros-args -p`는 launch 파일을 안 거쳐서 잘 됐고,
   그래서 초기 스모크 테스트가 이걸 못 잡았다 — **실제로 쓰는 경로(GUI)로
   확인해야 한다는 뜻이다.**
2. 고친 뒤에도 GUI의 "VLA 시작"이 그 인자를 **아예 안 보냈다.** 체크박스조차
   없어서 켤 방법이 없었다.

`test_gui_launch_arguments.py`가 이 둘을 막는다 — GUI가 보내는 인자가 launch에
선언돼 있는지, launch가 그것을 노드 파라미터로 실제로 넘기는지 검사한다.
**이런 종류의 인자를 추가할 때는 세 곳(GUI·launch 선언·Node parameters)을 다
건드려야 한다는 것을 기억할 것.**

---

### 6-C. 파서 프롬프트는 넓히면 다른 데가 좁아진다

"이거 집어줘"를 위층으로 보내려고 **"가리키는 말은 other"**를 넣었더니
`"여기 있는 거 다 담아줘"`까지 딸려 올라갔다. "여기 있는 거"가 가리키는 말처럼
읽혔기 때문이다.

증상이 성능이 아니라 **안전**으로 나온다는 점이 중요하다. 그 발화가 Tier 2로
새면 위험물 확인 게이트를 안 거치므로 **가위를 묻지도 않고 집는다.** 실제로
그렇게 동작했다.

"다/전부"가 붙어 범위를 통째로 가리키는 것은 손가락이 필요 없으니 `pick`이라고
프롬프트에 못 박았다. 파서는 검정으로 못 잡으니(LLM이다) 문장 9개를 직접
두드려 확인하는 수밖에 없다 — 프롬프트를 건드릴 때마다 하는 것이 좋다.

### 6-D. 두 계층이 같은 질문에 다르게 답할 수 있다

`pickable`이 그랬다. cobot2_ws 연동에서 `pick_fsm`은 클래스 이름만 받아 자기
카메라로 좌표를 내므로 이 ws의 `position_valid`는 파지의 전제가 아니다. 대화
경로는 그렇게 바뀌었는데 **규칙 계층은 옛 뜻으로 남아 있었다.**

합쳐진 채 두면 보정이 없는 실기 구성에서 Tier 1은 후보를 하나도 못 찾고
"담을 게 없습니다"라고만 한다. Tier 2는 같은 물체를 잘 집는다. 예외도 로그도
없어서 **"가끔 되고 가끔 안 된다"로만 보인다.**

`conversation.is_pickable()` 한 함수로 모았고, 두 계층의 답이 갈라지면 실패하는
검정이 있다. **판단에 쓰는 사실을 새로 추가할 때는 두 계층이 같은 곳에서 읽게
할 것.**

### 6-E. 무대의 결함이 제품의 결함처럼 보인다

`dryrun_stage`의 화살표가 아래에서만 찌르게 되어 있어 화면 아래쪽 물체는 꼬리가
프레임 밖으로 나가 사실상 안 그려졌다. 그림에 화살표가 없으면 모델은 짐작하지
않고 되묻는데 — **그게 맞는 동작이다** — 시험하는 쪽은 "가리켰는데 왜 되묻지?"로
읽는다. 하마터면 비전 기능이 고장 났다고 결론 낼 뻔했다.

가짜로 만든 것이 틀렸을 가능성을, 제품이 틀렸을 가능성보다 먼저 의심할 것.

|---|---|---|

가리킨 것은 명시적 지목이니 프롬프트 1번 규칙상 맞는 동작이기도 하다 — 그렇게
두기로 했다. 실기에서 문제가 되면 `SYSTEM_PROMPT`에 한 줄이면 된다.
